# Magic-link login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every app on Foyr can sit behind magic-link login: a visitor enters their email, clicks the link, and
authproxy forwards them to the app with `X-Foyr-User-Id`, `X-Foyr-Email` and `X-Foyr-Role`; the founder invites
people by email.

**Architecture:** foyrd serves the login pages on `auth.<PLATFORM_DOMAIN>`, stores users, members, invites,
single-use login tokens and codes, and signs session tokens with an Ed25519 key. authproxy checks the session on
every request with the public key, reads who may use which app from a snapshot it polls from foyrd (like
routes), and swaps a one-time code for a session at `/__foyr/callback` on each app host, so every app gets its
own host-only cookie (system-design 4c).

**Tech Stack:** Go 1.23+ stdlib (`crypto/ed25519`, `net/http`, `html/template`), pgx, Postgres 17, Resend HTTP
API for email, OpenTofu.

**Spec:** docs/superpowers/specs/2026-10-19-deploy-anything-design.md (Phase 1, item 1), system-design.md 4c and 4d.

This is plan 1 of 5 for Phase 1. Later plans: API tokens and public paths; customer dashboard; language
detection; founder Users and Platform pages.

## Global Constraints

- Branch `feat/login` from `main` after PR #29 (founder page) is merged; commits `git commit -s`; PR, never push to main.
- No hardcoded domains: `PLATFORM_DOMAIN` (foyr.online) gives `auth.` and `app.`; `APPS_DOMAIN` from config.
- Every state change writes its audit event in the same transaction; every tenant row carries `installation_id` (ADR-026). `users` is global (one person, many apps) and has none.
- New tables only in `internal/db/migrations/005_auth.sql`; never edit 001 to 004.
- Secrets live in SSM and `~/.config/foyr/`; never logged, never in the repo. Raw tokens and codes are never stored: only their SHA-256.
- Login token: 32 random bytes, 15 minutes, single use. Auth code: 32 random bytes, 60 seconds, single use, bound to one app. Session: 7 days.
- Cookie: `__Host-foyr_session`, host-only, `Path=/`, `HttpOnly`, `Secure`, `SameSite=Lax`.
- Roles: `owner > admin > member > viewer`. Access modes: `private` (default for new apps), `public`.
- Apps that exist when 005 runs become `public`, so foyr-hello keeps serving until the founder flips it.
- authproxy does no login checks while `FOYR_SESSION_PUBLIC_KEY` is empty (today's behavior), so code can ship before keys exist.
- One-line comments; no em dashes; failing test first for bugs.
- Checks before every commit: `gofmt -l . && go vet ./cmd/... ./internal/... && go test ./cmd/... ./internal/...` (store tests need `FOYR_TEST_DATABASE_URL`, docs/dev/database.md).

## Review Focus

- **Email scanners open links before people do.** Outlook and Gmail prefetch GET links; a GET of the verify link must not use the token. It shows a "Continue" button that POSTs. Test in Task 5.
- **Return paths that leave the app.** `return=//evil.com`, `/\evil.com`, `https://evil.com`, `/%2F%2Fevil.com` all become `/`. Test in Task 2.
- **The login form must not tell strangers who is a member.** Member, non-member and unknown app get the same page and status. Test in Task 5.
- **Emails typed differently.** `" Arpit@Gmail.COM "` matches an invite for `arpit@gmail.com`. Test in Task 3.
- **What the app receives.** The session cookie and any visitor-sent `X-Foyr-*` header never reach the app; only authproxy's own headers do. Test in Task 7.
